# 简历与面试说明

## 项目描述

基于 Qt 6、QML 与 C++17 开发 Windows/Android 跨平台局域网通信应用，整合设备发现、可信配对、即时消息、大文件续传、视频通话与屏幕共享，并完成 SQLite 离线存储、Android SAF/前台服务和 Windows 自包含发布。

## 推荐简历要点

- 设计 UDP 组播发现与 TCP 控制长连接状态机，支持可信设备配对、指数退避重连、双向连接收敛及离线历史查看。
- 实现基于 `.part` 文件、持久化任务和 SHA-256 的大文件断点续传；自动测试覆盖 64 MiB 中断恢复、非零偏移续传及校验失败重试。
- 引入随机挑战与 HMAC-SHA256，对控制重连、文件报价和媒体握手进行认证，阻止设备 ID 冒充、同 IP 错误密钥呼叫和伪造接听。
- 使用 SQLite/WAL 与 QSettings 持久化消息、传输任务和本地设置；针对 Android 实现 SAF 持久 URI 权限、前台服务、WakeLock 与 MulticastLock。
- 建立 CTest 集成测试、QML 冒烟测试和 `windeployqt` 部署验证，生成可脱离 Qt 开发环境运行的 Windows ZIP 与 Android APK/AAB。

## 面试时要主动说明的边界

- 当前是局域网点对点产品，不经过云端中继。
- HMAC 提供身份认证，但 TCP 内容尚未使用 TLS 加密。
- 视频采用受控帧率的 JPEG、音频采用 PCM over TCP，目标是局域网功能验证，不应描述为 WebRTC 商用品质。
- 自动化测试不能证明 Android 厂商后台策略和 MediaProjection 行为，真机结果应引用 `qa-matrix.md`。

## 常见追问

### 为什么 UDP 只用于发现？

UDP 组播适合低成本发现，但没有连接状态和可靠交付；设备找到后使用 TCP 完成配对、消息、文件和媒体控制。

### 如何解决 TCP 粘包？

每个包使用固定长度头记录负载长度，再携带消息类型与序列化内容；接收端缓冲数据，只有完整帧到达后才解析，并限制最大帧长度。

### 续传如何保证文件正确？

接收端将未完成内容写入 `.part`，重新连接后返回当前偏移；发送端从该偏移继续。完成后双方使用 SHA-256 校验，成功后再进入最终路径。

### 为什么不能只相信设备 ID 或 IP？

设备 ID 来自可伪造的广播，IP 也可能被复用。因此首次人工配对后保存随机密钥，后续连接通过随机挑战和 HMAC 证明身份。
